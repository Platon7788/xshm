# Межъязыковый контракт xshm 1.0 / xipc 2.2+

Единственная реализация wire-протокола находится в `xhook/ipc`. Rust xshm
линкует её через xipc-sys; самостоятельного Rust-протокола нет. Нормативны
заголовки `xhook/ipc/include/xipc/` и документация xhook `xipc.md` / `xipc.ru.md`.

Общий формат памяти: `0x00020000`, рукопожатие ревизии 3. C/C++ и Rust
должны использовать совместимые версии C-ядра. Политика безопасности по
умолчанию — текущий пользователь и SYSTEM. PID регистрации диагностический.

## Проверки

Rust: все unit/integration/doctests, x86/x64 Debug/Release, Clippy и rustdoc.
C: 38 native IPC suites, каждая в четырёх конфигурациях. Отдельно installed
SDK consumers (C, C++, Rust ABI), CRT-free consumers и hosted ASan.

`examples/interop_peer.rs` — Rust-пир для шести нативных наборов xhook:
single, session, Multi, Dispatch, namespace, beacon. Использует публичный
API xshm 1.0. CLI-сценарии оркестратора сохраняются как тестовый протокол;
библиотека не содержит прежнего API или переходных aliases.

```powershell
$env:XIPC_SOURCE_DIR = 'D:/GitHub/VsProjects/xhook/ipc'
pwsh D:/GitHub/VsProjects/xhook/scripts/run_interop.ps1 -Repeat 2
```

Матрица: C x86/x64 × Rust x86/x64, шесть suites, два повтора (48 запусков).
Проверяются payload/границы/PAD/асимметричные кольца, backpressure, последние
кадры и смерть процесса, повторные сессии, stale claims, Multi/Dispatch,
разные start orders namespaces, маяки и повреждённые ring headers.

Реальные тесты prof-shm дополнительно проверяют обе разрядности и их
смешанные пары, команды управления, историю, переподключение и завершение
процесса без Drop. Прикладной протокол профайлера описан в
`useful-lib/prof-shm/PROTOCOL.md`.

## Идентификаторы требований транспорта R1–R18

Метки сохраняются для ссылок прикладного протокола prof-shm. Это требования
к общему C-ядру, а не инструкция писать отдельный Rust-протокол. Точные
переходы состояний, барьеры и обработка ошибок определяются C-реализацией.

| Метка | Требование |
|---|---|
| R1 | Публикация write_pos, барьер и проверка пустого края для DATA; перед сном читатель делает барьер и повторную проверку. |
| R2 | Чтение, опустошившее кольцо, будит SPACE. |
| R3 | Достаточное место снимает соответствующий space_waiter через CAS и будит SPACE. |
| R4 | CLIENT_HELLO сопровождается CONNECT_REQ. |
| R5 | Подтверждение сервером рукопожатия сопровождается CONNECT. |
| R6 | PID и время создания пира публикуются до его участия в рукопожатии; ожидание процесса закрепляет идентичность. |
| R7 | Локальный уход публикуется после последних данных и сигналит DISCONNECT, включая уход из-за собственной ошибки. |
| R8 | Запрос регистрации лобби сигналит C2S_DATA. |
| R9 | Ответ лобби, включая отказ, сигналит S2C_DATA. |
| R10 | Маяк — NotificationEvent; raise после создания лобби, lower перед его закрытием. |
| R11 | Dispatch-клиент подключается к выданному каналу в пределах настроенного channel_connect_timeout. |
| R12 | Мьютекс лобби сериализует обмен регистрацией в лобби; освобождение/abandoned mutex обрабатывает C. |
| R13 | Multi поддерживает события слотов и обнаружения, ограничивает обход/пачки и сохраняет идентичность сессий. |
| R14 | Уход пира не эхо-сигналится; последние кадры дочитываются перед событием отключения. |
| R15 | Клиент учитывает generation и подтверждённое рукопожатие, включая ранний уход сервера с последними данными. |
| R16 | Сервер фиксирует новую сессию и устраняет устаревшие сигналы до публикации подтверждения. |
| R17 | Multi сохраняет исключительность заявки слота и освобождает чужую заявку только по подтверждённой смерти владельца. |
| R18 | Single также использует исключительную заявку и проверяемую идентичность владельца; проигравший не меняет состояние сессии. |
